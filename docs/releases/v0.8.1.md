# data-olympus 0.8.1

Every fix in this release came out of verifying 0.8.0 against a running
deployment. One of them changes what a bundle has to satisfy: a `supersedes` or
`superseded_by` edge that points at nothing is now refused on write and fails
lint, and the knowledge format moves to `0.4` to record that. Read
[Upgrading](#upgrading) before you roll this out to a bundle that has a lint
warning backlog.

## Fixed

### A supersession that names a missing document is refused

A document that says `supersedes: ADR-012` is meant to retire ADR-012. If no
document has that id, it retires nothing, and whatever it was written to replace
stays in force. A `superseded_by` naming a missing id records a successor that
does not exist. Both used to pass the write gate with a lint warning, which is
easy to miss and says nothing about the rule still governing.

A write that introduces such a target is now refused as
`rejected_invalid_document`. The reason starts with
`unresolved_supersedes_target` or `unresolved_superseded_by_target`, or with
`malformed_supersedes` / `malformed_superseded_by` when the value has the wrong
shape. A blank or whitespace-only target counts as malformed. Target strings are
compared exactly as written.

The check reads the commit the write is actually landing on, with the write
applied, so:

- a successor and its predecessor created in the same bootstrap bundle resolve
  against each other;
- a target that only exists as a pending proposal does not resolve, and neither
  does an id the same write removes;
- a target of any status resolves, including a retired document.

Existing content keeps working. A target already present in the committed
version of the file keeps passing, and so does a malformed value left exactly as
it was, so legacy documents can still be edited. "Exactly" is type-exact: `1`
changed to `true` is a change. Removing either field is always accepted. If the
commit cannot be read, the write is refused as `unresolved_target_unverifiable`
rather than let through unchecked.

Two proposals already pending that name each other (`A.supersedes: B`,
`B.superseded_by: A`) cannot both be approved as written. Approve A with
`edited_text` that drops the edge to B, approve B, then propose the edge on A
again. [`docs/serving.md`](../serving.md) describes this and the other edge
cases.

`data-olympus lint` and `data-olympus import` now report an unresolved target as
an error instead of a warning. `contradicts` keeps its warning. Two options
support this on both commands:

- `--resolve-root <dir>` resolves targets against a larger bundle, for linting a
  subtree or importing into an existing bundle.
- `--unresolved-targets warn` restores the warning while you work through a
  backlog.

Validating a write also got much cheaper. It used to start one git process per
document to look for duplicate ids. It now reads the committed tree with three
git processes for the whole write. On a 487-document corpus that took validation
from 10 to 16 seconds down to about 0.2 seconds.

A bootstrap bundle refused by its commit-time checks now says why: the response
carries a `reason`, redacted wholesale if it would contain credential-shaped
content. Refusals that happen earlier (path, size and rate limits) are
unchanged. The commit-time checks run in a fixed order: every file is
secret-scanned before duplicate ids or content defects are reported, so no later
diagnostic can echo a credential. (#259)

### A proposal with a malformed base marker is refused when it is made

`kb_propose_edit` accepted any string as `target_file_hash` or `base_blob_sha`.
A git blob id supplied in the sha256 field parked a proposal that could never be
approved: every approval returned `rejected_stale_base`, although the file had
not changed.

Both markers are now checked when the proposal is made. `base_blob_sha` must be
a 40-character lowercase hex git blob id, and `target_file_hash` a 64-character
lowercase hex sha256. Either may be omitted. Any other form is refused as
`rejected_invalid_base`, naming the field without echoing its value.

A proposal parked by an earlier release with a bad marker still cannot be
approved. Reject it and propose the same content again. (#263)

### An approval's claim record no longer keeps the edited text

Approving with `edited_text` wrote the full text into the claim record on the
state volume. Nothing reads it back. After an interrupted approval whose outcome
could not be proven, the text stayed there indefinitely, including text
committed under the explicit secret-scan override.

The claim now records only a sha256 digest of the approved content. Recovery
behaves exactly as before. A claim written by 0.8.0 keeps its text until a
reconciliation pass examines it, which happens once the claim is older than
`KB_PENDING_CLAIM_TTL_SEC` (900 seconds by default); that pass replaces the text
with the digest. (#264)

### `kb_list_pending` no longer fails on one damaged claim

A claimed entry whose `reconcile` value was not an object, for example a string
left by a hand edit, raised an error that hid every other entry in the listing.
It is now listed as `claimed`, which is how the running-contest check already
reads it. (#265)

## Knowledge format 0.4

The format spec moves from `0.3` to `0.4` for the supersession rule above.
Section 10 of [`SPEC.md`](../../SPEC.md) now states when a pre-`1.0` minor
version may tighten validation: only when the looser rule let a conformant
document silently fail to do what it declares, with each tightening recorded
alongside its migration path. From `1.0` onward, anything that makes a
conformant bundle fail validation needs a major version.

Nothing else about reading, parsing or validating a bundle changes. Bundles
created by `data-olympus init` declare `spec_version: "0.4"`.

## Upgrading

No configuration change is required.

**Lint and import can now exit 1 on a bundle that passed before.** An unresolved
`supersedes` or `superseded_by` target is an error. To migrate:

```bash
data-olympus lint <bundle> --unresolved-targets warn
```

Fix or remove each target it lists, then drop the flag. When linting part of a
bundle, add `--resolve-root <bundle root>` so targets elsewhere in the bundle
resolve.

**Writes that add a dangling target are refused.** An agent that proposes a
document superseding one that does not exist yet now gets
`rejected_invalid_document`. Create or import the predecessor first, or send both
in one bootstrap bundle.

**Bootstrap reports secrets first.** When a bundle has both a credential-shaped
file and a duplicate id or content defect, the response is now
`rejected_secret_detected`. Structural path checks still run before any of these.
