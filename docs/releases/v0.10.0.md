# data-olympus 0.10.0

A minor release about serving a knowledge base that does not look like ours. It
removes the assumption, wired into every git operation the server ran, that the
repository's trunk is called `main`, and it corrects a section of the serving
documentation that had been describing session reaping as it behaved before
0.3.3. Upgrading is recommended for anyone whose knowledge base lives on
a branch other than `main`, and is optional otherwise. No configuration change
is required: the new setting defaults to the previous behaviour.

## Added

### `KB_GIT_BRANCH`: the knowledge base's trunk is now a setting

Every git operation the server ran against the knowledge-base remote named
`main` literally, so a repository whose trunk is `master` could not be served at
all. The refresh loop's `git fetch origin main` failed, health stayed
`degraded`, and the index stayed frozen at whatever was built at startup. (#289)

Two further consequences were quieter than that warning. A write that supplied
an enforceable base marker was refused `rejected_stale_base`, because the
compare-and-swap base could not be refreshed against a branch the remote did not
have. Enforceable means a pinned `base_commit`, a `base_blob_sha` or a
`target_file_hash`; `base_commit: "HEAD"` is advisory and carries no per-file
expectation, so it does not trigger that refusal.

A write with no enforceable marker committed and then pushed `HEAD:main`, which
on such a remote creates a `main` branch. That branch is not inert: the refresh
loop fetches and merges `origin/main`, so from then on the server follows a
trunk its own writes invented, and changes made to the repository's real trunk
go on being ignored. The multifile write path behaves the same way, because it
suppresses a refresh failure and performs no compare-and-swap check.

`KB_GIT_BRANCH` now names that branch for the fetch, the fast-forward, the
session-worktree rebase that precedes a compare-and-swap write, the push, and
both reachability checks that decide whether a session worktree still holds
unpushed commits and may be garbage collected. That last one matters more than
it looks: measured against a branch the remote does not have, every worktree
looks unpushed, so none is ever reclaimed.

The value is validated when configuration loads rather than where it is used. A
value that is not a usable git branch name fails startup with the setting named
and the reason stated, which matters most for a value starting with `-`, because
git would read it as an option rather than a ref. A blank value means unset and
yields the default, the same rule the path settings already follow, so an
unsubstituted compose or Helm variable cannot turn into an empty ref name.

The supported subset is narrower than git's own grammar on purpose: ASCII
letters, digits, `.`, `_`, `-` and `/`, with git's structural rules (no
component beginning with `.` or ending `.lock`, no `..`, no `//`, no trailing
`/` or `.`) enforced at every level. `HEAD` and a fully qualified ref such as
`refs/heads/master` are refused as well, with a message saying to use the plain
branch name. Separately, every ref the server builds from the value is fully
qualified, so a branch name shaped like a ref path, or one that collides with a
tag, cannot be resolved into a different namespace.

The default is `main`, so a deployment that does not set it behaves exactly as
before.

## Changed

### The benchmark extra's `sentence-transformers` moved to 6.1.0

Lock only. The benchmark extra is not installed by the server or by the ordinary
test job, and the regenerated lock moves that one package with no transitive
dependency shared with a runtime package. (#285)

### The doc-consistency CI guard also checks documented configuration defaults

For each session-reaping variable, the guard reads every `(default ...)` the
prose of `docs/serving.md` states immediately after that variable, outside fenced
examples, and compares it with the corresponding `Config` field. Lowering a
default in code and updating only one of the places the documentation states it
now fails CI instead of ageing quietly. The guard reports the document line and
both values. It covers one document and one list of variables rather than every
setting the project has, and it requires the value as a whole number in the unit
the configuration uses, so a form it cannot read whole fails loudly instead of
being certified from its leading digits. (#286)

## Fixed

### Several documented settings were read and then silently ignored

`load_config()` read `KB_CONSULT_TTL_SEC`, `KB_PENDING_CLAIM_TTL_SEC`,
`KB_TRIGRAM_MODE` and `KB_TRIGRAM_FALLBACK_THRESHOLD` correctly, then the server
used their defaults, because `build_app` rebuilt its configuration from its own
keyword arguments and took none of them. (#291)

What that meant in a running server:

- the trigram typo and identifier fallback could not be enabled through the
  shipped entry point;
- the consultation freshness window was 300 seconds regardless of configuration,
  for `kb_consult`, `kb_gate_check` and the consultation ledger's retention;
- the claim guard used a 900-second claim TTL while the background sweep in the
  same process used the configured value.

None of this was new in 0.10.0. The production entry point now hands the loaded
configuration to the server unchanged, and a parity test names any
configuration field that fails to reach the running state.

### `docs/serving.md` described session reaping as it behaved before 0.3.3

The session reference section still said `KB_SESSION_IDLE_TIMEOUT_SEC` defaults
to `1800s / 30 min`, and still said a quiet long-lived `GET` SSE stream stamps no
activity and is reaped on that timer, with excluding open streams from reaping
listed as a possible follow-up. None of that has been true since the SSE
session-churn fix in 0.3.3: the default is `300`, the activity middleware runs a
keep-alive task for an open stream and re-stamps the session every
`KB_SESSION_TOUCH_INTERVAL_SEC`, and the server clamps that interval to at most
a third of the idle window. (#286)

The summary bullet near the top of the same document already described the
current behaviour, so the document contradicted itself, and the reference section
is the half an operator reads when sizing a client keep-alive. Both halves now
agree, and the corrected text states the condition the old text left out: the
reaper measures elapsed time since the last activity stamp, so a client that
polls less often than the idle window is reaped between calls.

## Upgrading

No configuration change is required, and no interface changed.

**If you set `KB_TRIGRAM_MODE`, `KB_TRIGRAM_FALLBACK_THRESHOLD`,
`KB_CONSULT_TTL_SEC` or `KB_PENDING_CLAIM_TTL_SEC`**, your value takes effect for
the first time with this release. Check that it is still what you want. In
particular, `KB_TRIGRAM_MODE=on` now builds and stores the trigram index at every
index build, which is the cost the setting's documentation describes and which
you have not been paying; and a longer `KB_CONSULT_TTL_SEC` now genuinely
lengthens how long one consultation satisfies the enforcement gate, and also how
long the consultation ledger keeps entries, so a large value grows the ledger
file.

**If your knowledge base's trunk is not `main`**, set `KB_GIT_BRANCH` to its
name. Check out that branch in `KB_MAIN_PATH` as well: the fast-forward merges
by ancestry rather than by name, so a checkout left on something unrelated is
the case that fails, and an intentional one is the clearest setup.

**If a server has already been running against such a remote**, check the remote
for a stray `main` branch created by an earlier write, because once it exists
the old refresh loop follows it and the server may have been serving content
from it while your real trunk was ignored. Compare the two before deleting
anything, and move across any commit that exists only on the stray branch.

**If you tuned a client keep-alive** from the old session reference section, read
it again. The numbers there were wrong, not the server's behaviour, so your
server was never reaping open streams; but a client that polls less often than
`KB_SESSION_IDLE_TIMEOUT_SEC` and holds no stream is reaped between calls.
