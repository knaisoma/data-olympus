# data-olympus 0.10.0

A minor release about serving a knowledge base that does not look like ours. It
removes the assumption, wired into every git operation the server ran, that the
repository's trunk is called `main`, and it corrects a section of the serving
documentation that had been describing session reaping as it behaved two
releases ago. Upgrading is recommended for anyone whose knowledge base lives on
a branch other than `main`, and is optional otherwise. No configuration change
is required: the new setting defaults to the previous behaviour.

## Added

### `KB_GIT_BRANCH`: the knowledge base's trunk is now a setting

Every git operation the server ran against the knowledge-base remote named
`main` literally, so a repository whose trunk is `master` could not be served at
all. The refresh loop's `git fetch origin main` failed, health stayed
`degraded`, and the index stayed frozen at whatever was built at startup. (#289)

Two further consequences were quieter than that warning. A write that supplied a
base marker (`base_commit`, `base_blob_sha` or `target_file_hash`) was refused
`rejected_stale_base`, because the compare-and-swap base could not be refreshed
against a branch the remote did not have. A write with no base marker committed
and then pushed `HEAD:main`, which on such a remote creates a `main` branch that
nothing subsequently reads, while the real trunk stays untouched.

`KB_GIT_BRANCH` now names that branch for the fetch, the fast-forward, the
session-worktree rebase that precedes a compare-and-swap write, the push, and
both reachability checks that decide whether a session worktree still holds
unpushed commits and may be garbage collected. That last one matters more than
it looks: measured against a branch the remote does not have, every worktree
looks unpushed, so none is ever reclaimed.

The value is validated when configuration loads rather than where it is used. A
value that is not a usable git branch name fails startup with the setting named,
which matters most for a value starting with `-`, because git would read it as
an option rather than a ref. A blank value means unset and yields the default,
the same rule the path settings already follow, so an unsubstituted compose or
Helm variable cannot turn into an empty ref name.

The default is `main`, so a deployment that does not set it behaves exactly as
before.

## Changed

### The benchmark extra's `sentence-transformers` moved to 6.1.0

Lock only. The benchmark extra is not installed by the server or by the ordinary
test job, and the regenerated lock moves that one package with no transitive
dependency shared with a runtime package. (#285)

### The doc-consistency CI guard also checks documented configuration defaults

For each session-reaping variable, the guard reads every `(default ...)` the
prose of `docs/serving.md` states immediately after that variable, outside fenced
examples, and compares it with the corresponding `Config` field. Lowering a
default in code and updating only one of the places the documentation states it
now fails CI instead of ageing quietly. The guard reports the document line and
both values. It covers one document and one list of variables rather than every
setting the project has, and it requires the value as a whole number in the unit
the configuration uses, so a form it cannot read whole fails loudly instead of
being certified from its leading digits. (#286)

## Fixed

### `docs/serving.md` described session reaping as it behaved before 0.3.3

The session reference section still said `KB_SESSION_IDLE_TIMEOUT_SEC` defaults
to `1800s / 30 min`, and still said a quiet long-lived `GET` SSE stream stamps no
activity and is reaped on that timer, with excluding open streams from reaping
listed as a possible follow-up. None of that has been true since the SSE
session-churn fix in 0.3.3: the default is `300`, the activity middleware runs a
keep-alive task for an open stream and re-stamps the session every
`KB_SESSION_TOUCH_INTERVAL_SEC`, and the server clamps that interval to at most
a third of the idle window. (#286)

The summary bullet near the top of the same document already described the
current behaviour, so the document contradicted itself, and the reference section
is the half an operator reads when sizing a client keep-alive. Both halves now
agree, and the corrected text states the condition the old text left out: the
reaper measures elapsed time since the last activity stamp, so a client that
polls less often than the idle window is reaped between calls.

## Upgrading

No configuration change is required, and no interface changed.

**If your knowledge base's trunk is not `main`**, set `KB_GIT_BRANCH` to its
name. Make sure `KB_MAIN_PATH` has that same branch checked out, or the
fast-forward has nothing to advance and health stays degraded. If the server has
been running against such a remote, check it for a stray `main` branch created by
an earlier marker-free write; nothing reads it, and it can be deleted once you
have confirmed its commits are also on your trunk.

**If you tuned a client keep-alive** from the old session reference section, read
it again. The numbers there were wrong, not the server's behaviour, so your
server was never reaping open streams; but a client that polls less often than
`KB_SESSION_IDLE_TIMEOUT_SEC` and holds no stream is reaped between calls.
