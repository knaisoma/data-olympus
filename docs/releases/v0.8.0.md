# data-olympus 0.8.0

Scheduled availability 2026-09-21. Until this version is published, that date is
a plan, not a record.

Two failures in this release were found by running the service, not by reading
it. A 3.6 MiB corpus needed more than a gigabyte of memory to index, so the
container was OOM-killed on every rebuild. And a dropped connection during an
approval left the write pipeline wedged on one path, invisibly, across a
restart. Both are fixed. The third change lets somebody outside this project
check the published benchmark numbers against their own run.

## Fixed

### Indexing a modest corpus no longer needs more than a gigabyte

Co-occurrence query expansion learns, at index-build time, which terms appear
together more often than chance. Building that table counted every distinct
token pair in the corpus in one in-memory table.

`KB_COOCCURRENCE_MAX_DOC_TOKENS` (400) bounds how much any single document
contributes. Nothing bounded the union across documents, and the union is what
is held. On a corpus of 536 markdown files totalling 3.6 MiB that was 6,202,615
distinct pairs and a peak of 1445 MiB, which is above a 1 GiB container limit on
its own, before the serving process is counted. Every rebuild ran into it, and a
rebuild fires on every corpus change.

Four bounds now apply. Three are lossless by construction:

* A term appearing in fewer documents than `KB_COOCCURRENCE_MIN_COUNT` cannot be
  in any pair that clears that threshold, because a pair only co-occurs where
  both terms appear. Those terms are dropped before pair counting, which removed
  5,947 of 11,070 terms on the corpus above.
* Pairs are keyed by a dense integer rather than by a tuple of two strings.
* Each term's candidate list is pruned to its top k as it accumulates, using the
  same total order the final sort uses.

The fourth is a ceiling you can set. Once the counter holds
`KB_COOCCURRENCE_MAX_PAIRS` distinct pairs (default 500,000) it is flushed into
a temporary SQLite database and cleared, and the counts are aggregated back at
the end.

The related-terms table produced is byte-for-byte identical, so **no search
result moves**. On that corpus, measured on one machine:

| `KB_COOCCURRENCE_MAX_PAIRS` | peak RSS | build time |
| --- | --- | --- |
| (the behaviour before this release) | 1445 MiB | 6.6 s |
| `0`, no spill | 502 MiB | 3.2 s |
| `500000`, the default | 105 MiB | 16.3 s |

The default trades build time for a ceiling that does not grow with the corpus.
That trade is real: on this corpus the co-occurrence pass is about ten seconds
slower, and a rebuild happens whenever the corpus changes. If your deployment
has memory to spare, raise `KB_COOCCURRENCE_MAX_PAIRS` or set it to `0`, which
is both faster and smaller than the previous behaviour. These are measurements
from one corpus on one machine, not a production latency figure.

The bound is on pair counting specifically. Parsed documents, per-document token
sets and the candidate lists sit outside it, and the counter is checked between
documents, so it can exceed the cap by at most one document's own pairs.

A failed co-occurrence build no longer fails the index build. The spill writes
to a temporary file, so it can fail on a full or read-only disk; since the index
only rebuilds when the corpus changes and `/readyz` rejects a failed build, that
would have left the service unready until the next commit. It now logs a warning
and continues with no related-terms table: the index still serves, and only
query expansion is lost until the next successful build.

Reported as issue #252, with the reproduction that established the cause.

### A dropped connection during an approval no longer wedges a path

Approving a pending write claims the entry, holds its path lock, commits, and
then releases both. When the process died in between, the entry was left in a
**claimed** state that nothing could reach:

* `kb_list_pending` read only live entries, so a claimed one was invisible.
* The orphan-lock collector treated the claimed sidecar as a legitimate lock
  holder, so it never freed the lock.
* Pending-owned locks were never reclaimed by age.

Every write to that path was refused `rejected_path_lock_busy`, in the reported
case for eight hours and across a pod restart, while the queue read as empty.
An empty queue is indistinguishable from "every decision was applied", so the
operator reasonably believed the write had landed. It had not. Recovery meant
finding and deleting two files on the state volume.

**Entries are now visible.** Every entry carries a `state`: `pending`,
`claimed`, or `uncertain`. Claimed entries are listed rather than hidden. They
still do not count towards `pending_count`, because they are not awaiting a
decision. Health reports `path_locks` with each lock's `target_path`,
`owner_kind`, `pending_id` and age, not only `path_locks_held`, so a wedged path
is diagnosable from the health endpoint.

**Outcomes are reconciled from evidence, never from age.** A background pass
examines claims older than `KB_PENDING_CLAIM_TTL_SEC` (default 900 seconds). The
age only decides which claims to look at:

| What the write recorded | Outcome |
| --- | --- |
| A commit sha | Committed. The entry is consumed and never presented again. |
| A failure | Not committed. The entry returns to `pending` for re-resolution, keeping its path lock. |
| Nothing | The commit is searched for by its new `KB-Pending-Id` trailer on the recorded session ref. Found means committed; anything else is `uncertain`. |

To make that possible the write now records its own outcome durably before
anything else happens, the claim stores the effective approved content and the
branch the commit will land on, and every commit that satisfies an approval
names the claim it satisfied in a `KB-Pending-Id` trailer. The message and the
tree are part of the same commit object, so there is no interval in which the
content is committed and the link is not.

**An unproven outcome stays unproven.** A negative search is not treated as
proof that nothing committed. A rebase drops a commit that upstream already
acquired as an equivalent patch, and a squash rewrites the trailer away, so the
commit can be gone while the branch reads perfectly. Restoring on its absence
would offer an already-applied decision for approval a second time. Such an
entry becomes `uncertain`: it keeps its path lock deliberately, reports why, and
is re-checked on every later pass, so a transient unreadable repository resolves
itself. For the same reason, operations that rewrite session history defer while
a claim on that branch has begun its write.

`docs/serving.md` documents the states, the reconciliation table and the manual
recovery path for an entry that stays uncertain.

Reported as issues #253 and #254, both with corrections from the reporter that
changed the diagnosis.

## Added

### A third party can compare a reproduction against the published benchmarks

The benchmark tables in `WHY.md` and `docs/comparison.md` are labelled
maintainer-produced and not independently reproduced, and the repository already
committed a receipt binding the source commit, source tree, corpus, queries,
outputs and dependency lock. What was missing was a way to compare your run
against that receipt.

```bash
uv run python -m benchmarks.receipt compare \
    --reference /path/to/published-receipt.json \
    --candidate benchmarks/results/receipt.json
```

The report has two levels, because they fail independently:

| `reproduction_status` | Meaning |
| --- | --- |
| `reproduced` | Recorded inputs and recorded results both match. |
| `inputs_matched_results_differ` | Same declared commit, environment, commands, seeds and configuration; different artifacts. This is the discrepancy worth reporting. |
| `inputs_differ_results_matched` | Different declared inputs, same artifacts. |
| `unreproduced` | Both differ. |

`reproduction_status` is therefore the outcome of a comparison against a named
reference, not a property a single receipt can assert. A receipt missing a field
the comparison needs is rejected rather than counted as a match, since two
omissions are not agreement, and CI now fails if the committed receipt stops
being usable as a reference. Artifact digests are compared exactly; there is no
tolerance mode.

What it establishes is bounded, and stated in the output itself: the comparison
is over **recorded** inputs and **recorded** results. This tooling writes down
what a run declares. It does not execute or observe that run, so a match means
the two receipts agree, not that the same execution occurred. Until somebody
outside this project publishes a receipt against this reference, the published
tables stay labelled maintainer-produced.

`benchmarks/README.md` documents the reproduction sequence, which preserves the
reference receipt and does not rewrite the documentation tables, and how to
report a discrepancy.

Requested in issue #158.

## Upgrading

No configuration change is required and no behaviour you depend on changes.
Three new settings are available, all with working defaults:

| Setting | Default | Effect |
| --- | --- | --- |
| `KB_COOCCURRENCE_MAX_PAIRS` | `500000` | Distinct pairs held in memory before spilling. `0` disables the spill. |
| `KB_PENDING_CLAIM_TTL_SEC` | `900` | How long a claimed entry sits before reconciliation examines it. |

If you set `KB_COOCCURRENCE_MODE=off` to work around the memory problem, this
release is what lets you turn it back on. Verify your own corpus first: the
ceiling is on pair counting, and total rebuild memory also depends on corpus
size.

`kb_list_pending` entries gain a `state` field and now include claimed entries.
A caller that assumed every listed entry was awaiting a decision should filter
on `state == "pending"`.
