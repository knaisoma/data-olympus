# data-olympus 0.7.2

Dependency updates work again, and the release contract says what a security
alert must prove before a release can be handed over.

## Security

* **`cryptography` updated from 49.0.0 to 50.0.1**
  ([GHSA-g6cj-pr64-35w5](https://github.com/pyca/cryptography/security/advisories/GHSA-g6cj-pr64-35w5),
  high severity). PKCS#7 `EnvelopedData` decryption reported failures in
  distinguishable ways and with distinguishable timing, exposing a
  Bleichenbacher oracle to any application that decrypts attacker-supplied
  `EnvelopedData` and reflects the outcome. Data Olympus reaches
  `cryptography` only transitively and never calls the affected entry points,
  so no product code path was exploitable. The dependency is updated so that no
  vulnerable version is resolved or shipped.

## Fixed

* **Dependency updates are no longer blocked by a historical benchmark
  measurement.** The `benchmark-docs` guard compared the benchmark receipt's
  recorded `dependency_lock` against the *current* `uv.lock`, so every change
  to the lockfile failed CI with `dependency_lock does not match uv.lock` -
  security updates included. Those are two different facts: what one
  measurement ran under, and what the project depends on today. The guard now
  verifies the receipt against the lockfile as committed at the receipt's own
  measurement revision, still byte for byte, and lets current dependencies
  move. Tamper-evidence over the measured environment, benchmark sources,
  corpora, queries, and outputs is unchanged.
* **The receipt's recorded lock binding is corrected.** Its
  `dependency_lock.sha256` had been regenerated in place against a newer
  lockfile while the recorded measurement revision was left unchanged,
  describing a pairing that never existed. The binding is restored to the
  lockfile actually committed at that revision. No benchmark was re-run and no
  published number changed.
* Release admission requires a human merge and preserves published artifacts
  (#240).
* Operations reports why a command failed, not only which one (#230).
* The release no-action outcome is deterministic (#226).

## Changed

* **The release contract separates candidate remediation from post-merge alert
  closure.** Zero open security alerts remains mandatory before publication. A
  security alert is raised against the default branch, so the branch that fixes
  it cannot close it before merging. The contract now names that single narrow
  case, and requires per-alert proof that the fix is present in the exact
  reviewed candidate, agreement from both the implementer and the independent
  reviewer, and fresh zero-alert clearance after the merge before any artifact
  is published. No broader exception is granted.

## Upgrading

No action required. There is no runtime, API, CLI, MCP, or bundle-format
change in this release.
