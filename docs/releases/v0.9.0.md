# data-olympus 0.9.0

A minor release about trusting that what the knowledge base tells you is still
current, about letting a proposal say that it disputes existing knowledge, and
about a pending-lock surface that is correct, cheap and does not leak. It also
closes a gap where a write could be applied without an audit record. Upgrading is
recommended for every deployment. No configuration change is required, and the
one new setting is off by default.

## Added

### `kb_curate`: which in-force documents are due for review, most overdue first

`kb_search` and `kb_get` already reported a `freshness` signal per document, but
using it meant already knowing to filter for it. `kb_curate` aggregates that same
signal into one list, most overdue first, so the question "what needs a look?"
has a direct answer. (#142)

It is advisory and read-only, with no write-pipeline dependency, and it is
registered in read-only replicas alongside `kb_search` and `kb_get`. Candidates
are exactly the `kb_search(in_force=true)` set. Nothing being due for review is a
valid empty list, not an error.

The tool name is reserved on #31, which avoids a collision with the existing
`kb_audit` event-log tool. #31's actual request, detecting repeated patterns
across documents and proposing to hoist them up the tier chain, is NOT in this
release and #31 remains open. That work needs its own detection design.

### Review-due derived from how long a document has actually gone unverified

`last_verified` used to be advisory and evaluated by nothing, so a document
nobody had re-verified in two years looked exactly as fresh as one checked
yesterday. (#142)

With the new `KB_REVIEW_DUE_AFTER_DAYS` setting, a document with no explicit
`recheck_by` is reported `freshness: "stale"` once its `last_verified` is older
than that many days. A document with no `last_verified` at all is also `stale`,
deliberately: defaulting a never-verified document to fresh would hide exactly
the documents most worth looking at.

An explicit `recheck_by` remains an override in either direction. In the past, it
is `stale` regardless of verification age; in the future, it suppresses the
automatic check entirely. A new `freshness_reason` field on `kb_search` hits and
`kb_get` names the field and the date or day count behind a non-empty
`freshness`.

The setting is unset by default, so behaviour is unchanged until you set it. It
is advisory only and never affects `in_force` or default search.

### A proposal can declare that it contests existing knowledge

Until now a knowledge base could not tell a resolved contradiction from an ordinary
edit after the fact: nothing on a change recorded that it was disputing something.
`kb_propose_edit` now accepts an optional `contest` mapping naming the
`contradicts` document IDs and an optional dispute `reason`, so that intent is
recorded at the moment it is expressed. This is the first slice of #241.

**An accepted contest requires confirmation and is never auto-committed**, even at
high confidence with auto-commit otherwise permitted. Disputing in-force knowledge
is a human decision, never an automatic one.

Validation runs in two stages. Structural bounds and a credential scan run before
the rate limiter, so a structurally invalid contest costs no rate-limit budget.
Contradicted IDs are then resolved against the index after it, and a document that
contradicts itself is refused. A contest refusal never echoes a submitted ID or a
resolved path back to the caller. `kb_list_pending` shows the proposal's operational reason and its
dispute rationale as separate fields, so neither overwrites the other.

Which indexed documents are legitimate contest targets remains an open design
question on #241 and is deliberately not settled here.

This feature was designed and written by @RemanenetSpy in #278, who worked through
several rounds of review and answered each one. The two-stage validation around the
rate limiter and the dedicated `intent` field are their design, and holding back a
read-side projection until the access controls in this same release were ready was
their choice. It landed in #281 with maintainer follow-ups on top. Thank you.

## Security

### A write could be applied without an audit record

Caller-supplied text that cannot be encoded as UTF-8 passed every validation gate on
the write path. In an identity field it could cause the audit record for that
operation not to be written, while the operation itself succeeded, so a caller who
controlled only their own identity string could act without leaving a trail. Stored
in a pending entry, it also made the pending listing fail for every reader rather
than only for that one record. (#280)

Identity and routing fields are now refused with `rejected_invalid_encoding` before
any other validation or side effect inside the write functions, and a resolve
refused this way returns HTTP 400. The proposal `reason` is replaced rather than
refused, matching how a credential in that field is already handled; unencodable
`evidence` items and contest strings are refused. The pending listing, the pending detail response and the health
lock view now degrade an unreadable value to a placeholder instead of failing the
whole response, which also covers entries written before this release. Correctly
formed non-ASCII text, including emoji and accented or CJK paths, is unaffected.

### Health no longer hands pending ids to unauthenticated callers

`GET /api/v1/health`, the degraded 503 body that every read route can return, and
MCP `kb_health` each carried a `path_locks` record per held lock, including its
`pending_id`, and none of them required a token even when auth was configured.
Every other pending-queue surface (`kb_list_pending`, `kb_get_pending`,
`GET /api/v1/pending`) already required one. (#270)

With auth configured, those records now omit `pending_id` for a missing or
invalid token. A valid token still sees it, and the operator use case the field
was added for, finding which path is wedged, needs only the path and the age.
Behaviour is unchanged when auth is not configured.

Redaction is an allow-list over lock-record fields rather than a `pending_id`
special case, so a field a later release adds to the lock does not become
readable by default. Responses served with auth configured now also carry
`Cache-Control: private` and `Vary: Authorization`, so an intermediate cache
cannot serve one caller's body to another.

## Fixed

### A path lock is published atomically, and a failed publish no longer strands it

The lock file used to be created empty and then written into, so a reader could
observe an existing-but-empty or truncated lock for the duration of the write. It
is now written complete to a private temp file and published with a single
`os.link`, which still fails if the path is already locked, so exclusive-create
semantics are unchanged. (#272)

Separately, `atomic_write_json` publishes a pending entry before its trailing
parent-directory fsync. A failure in that fsync used to release the entry's lock
unconditionally even though the entry was already live on disk, which let a
second proposal take the same path. The lock is now released only when the entry
never actually landed.

A crash-leftover publish temp file is reaped by the existing periodic GC pass,
past the auto-commit lock TTL. See `docs/operations.md` section 4.6.

## Changed

### Healthy REST reads no longer enumerate or read every path lock

The degraded-precheck that every read route runs first listed the lock directory
and opened and parsed each `*.lock` file, even though it only needed to know
whether the index was degraded. Cost therefore scaled with the size of the
pending queue on the overwhelmingly common healthy path. (#271)

`get`, `search`, `outline`, `list`, `/readyz` and `/metrics` now skip the
enumeration entirely when the index is healthy. A degraded response still carries
the full `path_locks` list in its 503 body.

### The benchmark receipt is checked for a reachable `source_commit` before merge

A receipt refreshed on a pull request branch named a commit that the squash merge
then removed from `main`, so the benchmark-docs guard passed on the pull request
and failed afterwards, and a reproduction could not check out the revision the
numbers were measured at. CI now fails a pull request that introduces such a
receipt, with a message explaining how to re-measure. `benchmarks/README.md`
documents the resulting workflow. (#268)

### Writing rules are enforced in CI

The project's documentation had accumulated banned punctuation and phrasing that
kept reaching public output. A lint step now fails a pull request that introduces
them, and the existing prose was corrected to match. Documentation and punctuation
only: no runtime behaviour or interface changed. (#282)

## Upgrading

No configuration change is required.

**If you run with auth configured** and something of yours reads `pending_id`
out of an unauthenticated health response, it needs a valid token now. Nothing
changes when auth is not configured.

**If you want the new review-due behaviour**, set `KB_REVIEW_DUE_AFTER_DAYS`.
Leaving it unset keeps the previous behaviour exactly. Before setting it, expect
documents that have never been verified to start reporting `freshness: "stale"`,
which is the point, but it can be a large set the first time.

**If you cache health responses** with auth configured, note the new
`Cache-Control: private` and `Vary: Authorization` headers.

**If a client handles write-path responses**, there is one new refusal status,
`rejected_invalid_encoding` (HTTP 400). It is returned when `agent_identity`,
`source_session`, `target_path`, `base_commit`, `base_blob_sha`,
`target_file_hash`, or on resolve `pending_id` or `edited_text`, contains text that
is not valid UTF-8. The identity and routing fields are also refused if they are
not strings at all. A client sending well-formed text never sees it.

**If you want to record a dispute**, pass the optional `contest` mapping to
`kb_propose_edit`. Callers that do not send it see no change.
