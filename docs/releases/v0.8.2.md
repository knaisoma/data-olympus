# data-olympus 0.8.2

A patch release with one security hardening change and one availability fix.
Upgrading is recommended for every deployment, and no configuration change is
required.

## Security

### MCP validation errors and server logs no longer repeat what a caller sent

When an agent called a tool with arguments of the wrong shape, the error it got
back and the warning the server logged both included the submitted value, and
for an unexpected argument its name, so a value sent in the wrong field ended up
in the server log. Other diagnostics in the MCP stack could carry request
content too: debug traces of call arguments and response chunks, tracebacks
whose messages quoted the request, the SDK's report of a malformed message, and
query strings in access logs.

A call whose arguments fail validation, or that names an unknown tool, now gets
a short message that names the parameter and the rule without the value, for
example `confidence must be a number (float_parsing)`. That holds for direct
calls and for calls made through the search-mode `call_tool` proxy.

Log records emitted by the MCP SDK, FastMCP (excluding its client modules) and
`sse_starlette` are rewritten before they are written:

- message arguments become `<redacted>`, except the request type in the SDK's
  request trace and the tool name in the invalid-arguments warning;
- a message that arrives already formatted becomes a marker naming its source
  file and line, so you can still find which diagnostic fired;
- tracebacks keep their frames and exception types, up to a nesting limit, with
  exception messages replaced by `<message redacted>`.

Uvicorn access lines keep the method, path and status and drop the query string.
Log records from Data Olympus itself are unchanged.

What does not change: an error raised by a tool while it runs, such as
`kb_search` explaining that `validity_state` expects a number of days, is still
returned to the caller as before. It only goes back to whoever sent the request
and tells them how to fix it. A pydantic validation error raised inside a tool
is summarized the same way as an argument-validation error.

## Fixed

### A malformed lock file no longer takes down health, readiness and reads

A path lock whose content was valid JSON but not an object, which the server
never writes itself but a partial restore or a hand edit can leave behind, made
the lock listing raise. Health, the `/readyz` readiness probe, `/metrics`, MCP
`kb_health` and every REST read route build health first, so all of them failed,
and repeated readiness failures take the pod out of its Service. (#269)

The file is now listed in health as `owner_kind: "unreadable"` with null fields,
and the orphan collector and stale auto-commit reclaim leave it in place because
its owner cannot be established. Remove it by hand once no write to that path is
in flight.

## Upgrading

No configuration change is required.

**Clients that parsed pydantic's raw validation text** will see the shorter
message described above. The error is still reported as a tool error and still
names the parameter.

**Operators reading MCP-layer logs** will see `<redacted>` in message arguments,
source-location markers in place of preformatted messages, and
`<message redacted>` in tracebacks. Data Olympus's own log records, including
startup and git diagnostics, are unchanged. If you relied on query strings in
uvicorn access logs, they are no longer recorded.
