# Per-artifact SBOMs

Every reusable candidate artifact carries its own SBOM, bound to its digest
(SDLC section 9). The candidate artifacts are the wheel, the sdist and the OCI
image, which has one document per platform manifest. All documents are SPDX
2.3 JSON generated by a pinned syft.

| Subject | Document (candidate release asset) | Contents | Attestation subject |
| --- | --- | --- | --- |
| Wheel | `<wheel>.spdx.json` | The extracted wheel plus the runtime dependency closure exported from the candidate's `uv.lock` without the dev group | The wheel's SHA-256 |
| Sdist | `<sdist>.spdx.json` | The extracted sdist plus the same exported closure | The sdist's SHA-256 |
| Image, linux/amd64 | `image-linux-amd64.spdx.json` | The scanned image filesystem (OS and Python packages) | The amd64 platform manifest digest |
| Image, linux/arm64 | `image-linux-arm64.spdx.json` | The same for arm64 | The arm64 platform manifest digest |

syft does not look inside wheel or sdist archives, so stage one extracts them
and scans the tree. The closure in the package SBOMs is the set the candidate
was built and tested with. A consumer installing the wheel from PyPI resolves
its own dependency versions within the declared ranges.

## Generation (rc-build.yml, stage one)

- syft `1.52.0`, downloaded from the Anchore GitHub release and checked against
  the published SHA-256 of `syft_1.52.0_linux_amd64.tar.gz` before it runs.
  Changing the version means updating `SYFT_VERSION` and `SYFT_SHA256` in
  `rc-build.yml` and `SYFT_VERSION` in `scripts/sbom_evidence.py` together.
- Image documents are generated from the OCI archive (`oci-archive:` with
  `--platform`), before anything is pushed. The root package of each names
  `ghcr.io/knaisoma/data-olympus` and carries the platform manifest digest as
  its SHA-256 checksum.
- After `release_artifacts.py finalize-archive`, `sbom_evidence.py embed`
  validates the documents against that provenance (archive hash, image index,
  wheel and sdist hashes) and records them in `release-provenance.json` under
  `sboms`: subject,
  subject name, subject digest, document file name and SHA-256, predicate type
  and generator.

Stage one runs candidate code, so these documents are untrusted input until
stage two binds them.

## Binding and attestation (rc-publish-stage.yml, stage two)

The verifier (`scripts/sbom_evidence.py`, called by `rc_verify_and_publish.py`)
recomputes the subjects from the artifacts it verified: the wheel and sdist
hashes, and the platform manifests of the image index whose digest it checked.
The receipt must list exactly those subjects in a fixed order; each document
must have the recorded hash, be SPDX 2.3, name the pinned syft as creator, list
components besides its root, and (for the image) carry its platform manifest
digest. Reads are bounded at 16 MiB, the `actions/attest` limit.

The documents then travel like every other candidate asset: they are uploaded
to the draft release, read back byte for byte, and their hashes are part of the
annotated candidate tag message.

The `attest` job, which runs no repository code, copies the four documents,
checks their names and hashes against the `publish` outputs, and signs each
with `actions/attest` (pinned by SHA). The predicate type is
`https://spdx.dev/Document/v2.3`. The image attestations are also pushed to the
registry.

A candidate built from a `release/new` whose `rc-build.yml` predates SBOMs has
no `sboms` receipt and no `sbom/` directory. Stage two still publishes it (a
staging candidate), with `sbom=false` and no SBOM attestations. Promotion
refuses it.

## Verification (promote-release.yml)

The `prove` job, before any publication:

1. Downloads the four documents from the candidate release.
2. Reads the raw image index of the recorded digest with `skopeo inspect --raw`
   and requires its SHA-256 to be that digest.
3. `sbom_evidence.py plan` requires the `sboms` receipt, the stored documents
   with their recorded hashes, the candidate files as subjects, and the index
   platforms as image subjects.
4. For each subject, `gh attestation verify` with the predicate type above and
   the same signer contract as the provenance check (`--signer-workflow
   .../rc-publish-stage.yml --source-ref refs/heads/main
   --deny-self-hosted-runners`). `sbom_evidence.py match` then requires a
   verified statement that names the subject digest and whose predicate is
   JSON-equal to the stored document.

Any failure stops the promotion.

## Release record

`release-record.json` gains an optional `sboms` list, a copy of the candidate
receipt entries. The key is additive, so `schema_version` stays `1`. Each
`file` is an asset of the release named by the record's `candidate_tag`.

The image entries describe the promoted image exactly, since the image is
promoted by digest. The wheel and sdist entries describe the candidate files.
The stable files are still rebuilt from `S` and compared with the candidate by
normalized payload ([stable Python artifacts](reviewed-promotion.md#stable-python-artifacts));
phase B step 10 replaces that rebuild with publication of the exact candidate
files, which makes these entries describe the published bytes too.

## Rollback

Revert the pull request. Candidates published while it was active keep their
extra assets and attestations, which nothing else reads.
